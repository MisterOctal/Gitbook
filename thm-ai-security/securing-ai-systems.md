# Securing AI Systems

**Date:** 15.04.2026

**Room Category:** Walkthrough&#x20;

**Core Concept:** Mapping AI architecture, identifying OWASP LLM Top 10 risks, and applying secure design patterns to AI trust boundaries.

Unlike traditional apps where we can easily map structured data flows, AI introduces unstructured natural language as a primary input. This shift creates a massive attack surface that traditional WAFs and input validation aren't designed to handle.

***

## Task 1: Introduction

TryAssist represents a major shift for TryTrainMe. It is an assistant that reads pull requests, queries internal docs, and hooks into the CI/CD pipeline. The risk here is that it acts on natural language instructions. If an engineer accidentally pastes proprietary code or credentials into the chat, that data leaves the company control. Understanding the architectural risks before deployment is my primary job here as a security architect.

## Task 2: Anatomy of an AI System

Transitioning from traditional apps to AI-augmented ones changes the security landscape. In a standard app, we deal with deterministic code and structured forms. With AI, we are dealing with probabilistic model inference and free-form text. TryAssist has nine specific components, ranging from the API Gateway to the Vector Store used for Retrieval-Augmented Generation (RAG).

<figure><img src="../.gitbook/assets/image (234).png" alt=""><figcaption></figcaption></figure>

We need to focus on the trust boundaries. These are the points where data moves between different security contexts. In TryAssist, there are five key boundaries:

* **User-to-system:** Where untrusted text enters.
* **System-to-LLM:** Where the full prompt (including system instructions) is sent.
* **LLM-to-tools:** Where model output triggers actions like database queries.
* **System-to-external-data:** Where retrieved documents enter the prompt.
* **System-to-user:** Where the final response is delivered.

Question: What layer in an AI system is responsible for combining the system prompt, user input, and retrieved context before sending it to the model?

> **Answer:** Prompt Construction

Question: In the TryAssist architecture, what boundary does LLM output cross when it triggers a database query?

> **Answer:** LLM-to-tools

***

## Task 3: The AI Attack Surface

To properly defend TryAssist, we use three primary frameworks. The OWASP LLM Top 10 (2025) helps me classify vulnerabilities like Prompt Injection or Excessive Agency. MITRE ATLAS (Adversarial Threat Landscape for AI Systems) gives a knowledge base of actual adversary tactics, similar to how I use ATT\&CK for traditional systems. Finally, the NIST AI RMF provides the high-level governance needed to manage these risks across the organization.

Question: Which OWASP LLM Top 10 (2025) category covers the risk of LLM output being used to execute SQL injection against a backend database?

> **Answer:** LLM05

Question: What is the name of the MITRE knowledge base specifically designed for adversary tactics and techniques against AI and ML systems?

> **Answer:** ATLAS

***

## Task 4: System-Level Threats

During the review, we specifically looking for five system-level threats that emerge from the architecture:

* **LLM10: Unbounded Consumption:** This is a resource exhaustion risk. If an attacker sends massive inputs or floods the API, they can drive up costs or crash the service.
* **LLM07: System Prompt Leakage:** This happens when the hidden instructions telling the LLM how to behave are revealed to the user. These prompts often contain internal API paths or business logic.

<figure><img src="../.gitbook/assets/image (236).png" alt="" width="188"><figcaption></figcaption></figure>

* **LLM05: Improper Output Handling:** This is critical. If we take text generated by the LLM and pass it directly to a shell or database without sanitizing it, we are inviting injection attacks.
* **LLM06: Excessive Agency:** This occurs when the AI is given too much power, such as the ability to delete database records or merge code without human approval.

<figure><img src="../.gitbook/assets/image (237).png" alt="" width="375"><figcaption></figcaption></figure>

* **LLM02: Sensitive Information Disclosure:** As seen with the Samsung leak, this is the risk of proprietary data being included in model training or stored in insecure conversation logs.

<figure><img src="../.gitbook/assets/image (238).png" alt="" width="375"><figcaption></figcaption></figure>

Question: The Air Canada chatbot incident is frequently cited as an LLM05 example, but OWASP LLM Top 10 (2025) classifies it under which category?

> **Answer:** LLM09

Question: What are the three dimensions of excessive agency?

> **Answer:** Excessive Functionality, Excessive Permissions, Excessive Autonomy

Question: A user extracts internal API endpoints from an AI assistant's system prompt. Which OWASP LLM Top 10 (2025) category does this fall under?

> **Answer:** LLM07

Question: An attacker sends thousands of maximum-length requests to an LLM API to generate a large bill. Which OWASP LLM Top 10 (2025) category covers this?

> **Answer:** LLM10

## Task 5: Secure Design Patterns

Securing an AI system requires defense in depth at every trust boundary. We can't just rely on one check. We need input length validation at the user-to-system boundary, system prompt hardening at the system-to-LLM boundary, and most importantly, human-in-the-loop for any write operations at the LLM-to-tools boundary.

<figure><img src="../.gitbook/assets/image (239).png" alt="" width="563"><figcaption></figcaption></figure>

The principle of Least Privilege is vital here. If the LLM needs to check a database, it should have a read-only account. If it needs to call an API, that token should be scoped only to the required endpoints. Integrating these checks into the MLSecOps lifecycle ensures that we aren't just bolting security on as an afterthought.

Question: What security principle states that every AI component should have the minimum permissions required to perform its function?

> **Answer:** Least Privilege

Question: What practice integrates security into the machine learning lifecycle, covering monitoring, observability, and incident response?

> **Answer:** MLSecOps

***

## Task 6: Auditing TryAssist: A Conversation with the System

To finish the audit, we interviewed the pre-deployment version of TryAssist. By asking direct questions about its capabilities and permissions, I surfaced several critical flaws that weren't obvious in the documentation.

<figure><img src="../.gitbook/assets/image (240).png" alt="" width="563"><figcaption></figcaption></figure>

I found that the assistant had "db\_admin" privileges, which is a massive violation of least privilege. It also admitted to being able to merge pull requests automatically without human intervention (Excessive Agency). Finally, it confirmed that it logs everything without any PII filtering, meaning any credentials pasted into the chat are sitting in plain text logs.

Question: During the audit, TryAssist describes one action it takes automatically, without requiring human approval. What is that action?

> **Answer:** Merge Pull Requests

Question: What database role does TryAssist report operating under?

> **Answer:** db\_admin

Question: TryAssist logs all conversations without applying which security control?

> **Answer:** PII Filtering

***

## Conclusion

Securing AI systems is an architectural challenge, not just a model-tuning one. We've learned that we must treat LLM output as untrusted input for downstream systems and that human oversight is non-negotiable for autonomous actions. By mapping trust boundaries and applying frameworks like OWASP and ATLAS, I can build a defense-in-depth strategy that protects both the data and the infrastructure supporting the AI.
